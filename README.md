# Naftali Studio Website

A Hebrew RTL website for Naftali — an artist and maker working with wood, stone, and boutique wood-and-glass creations, who also writes poetry.

The site presents his work as both an online shop and an intimate artist’s studio: Home, Poetry, Shop, and Contact, with a shopping cart foundation ready for later checkout.

Built with **Cursor** in phases: foundation → catalog API → poems & cart → polish & accessibility → UI & public packaging. The architecture is intentionally extensible.

## About the Project

Naftali’s work combines the warmth of village craftsmanship with a refined boutique feel.

This project provides a maintainable full-stack foundation so visitors can:

* Explore the studio story on the home page
* Browse poetry cards and open full poems
* Browse shop categories and product cards
* Add items to a local shopping cart
* See contact placeholders until real details are provided

The application is built as a full-stack project using Angular and FastAPI.

## Current Status

The project currently includes:

* Angular frontend with Home, Poetry, Shop, Contact, shared header/footer, cart preview, and login preview
* FastAPI backend with health, products, and poems APIs
* Typed Product and Poem schemas shared through REST
* Mock catalog data when PostgreSQL is unavailable
* Poems loaded from `backend/app/data/poems.txt`
* Shopping cart in the browser (localStorage), max one of each item, checkout marked “Coming Soon”
* Hebrew-only visitor UI with full RTL layout
* Product image placeholder when a real image is missing
* Same-origin API mode via Angular proxy in development, and SPA served by FastAPI after `ng build`
* Docker and `render.yaml` packaging for a future always-on public deploy

Login is a visual preview only. Payments, real authentication, WhatsApp newsletter, AI assistant, and admin tools are not implemented yet.

## Architecture

The application is two processes that talk over HTTP in development. In one-service mode, FastAPI also serves the built Angular SPA from the same origin.

```text
Browser (Angular)
    │
    │  GET /health
    │  GET /products[?category=]
    │  GET /products/{id}
    │  GET /poems
    │  GET /poems/{id}
    ▼
FastAPI
    ├── health router
    ├── products router  →  catalog service  →  PostgreSQL or mock products
    ├── poems router     →  catalog service  →  poems.txt / DB poems
    └── (optional) static SPA from frontend/dist/.../browser
```

### Why the split looks like this

The frontend is a presentation and interaction client: pages, cart UI, and navigation. The backend owns catalog and poem data and the API contracts. The cart stays in the browser for now so shopping works without accounts or checkout. That keeps the first foundation simple while leaving a clear place for server-side carts, orders, and auth later.

Secrets such as `OPEN_ROUTER_API_KEY` stay in root `.env` and are read only on the backend when AI is added. They are never exposed to Angular.

### Frontend layout

```text
frontend/src/app/
├── core/           shared API base URL
├── models/         Product, Poem, CartItem
├── services/       catalog HTTP client, cart state
├── pages/          home, poetry, shop, contact
└── shared/         header, footer, cards, cart preview, login preview, product image
```

`API_URL` is empty so requests stay same-origin. During `ng serve`, `proxy.conf.json` forwards `/products`, `/poems`, and `/health` to FastAPI. After a production build, FastAPI serves the SPA and the same paths.

### Backend layout

```text
backend/app/
├── main.py              app, CORS, optional SPA static hosting
├── schemas.py           Product, Poem, ErrorBody
├── data.py              mock products and categories
├── poems.py             poems.txt parser
├── database.py          PostgreSQL init (optional)
├── api/
│   ├── health.py
│   ├── products.py
│   └── poems.py
└── services/
    └── catalog.py       list/get products and poems
```

Routers stay thin. They validate input and call the catalog service.

### API

Interactive documentation is generated by FastAPI at `/docs`.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health` | Returns `{ "status": "ok" }` |
| `GET` | `/products` | Product list; optional `category` query |
| `GET` | `/products/{id}` | One product |
| `GET` | `/poems` | Poem list |
| `GET` | `/poems/{id}` | One poem |

Product categories: `mezuzahs`, `hanukkiahs`, `furniture`.

Unknown category → `400`. Missing product or poem → `404`.

## Running the Project Locally

Run the API first, then the SPA.

### Backend

Open a terminal in the `backend` directory:

```powershell
cd backend
```

Create a virtual environment:

```powershell
python -m venv venv
```

Activate it:

```powershell
.\venv\Scripts\Activate.ps1
```

Install the dependencies:

```powershell
python -m pip install -r requirements.txt
```

Run the FastAPI server:

```powershell
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

The backend will be available at:

```text
http://127.0.0.1:8000
```

FastAPI documentation:

```text
http://127.0.0.1:8000/docs
```

### Frontend

Open another terminal in the `frontend` directory:

```powershell
cd frontend
```

Install the dependencies:

```powershell
npm install
```

Run the Angular application:

```powershell
npx ng serve
```

The frontend will be available at:

```text
http://localhost:4200
```

### One-service mode

Build the frontend, then let FastAPI serve the SPA and the API together:

```powershell
cd frontend
npm run build
cd ../backend
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Open:

```text
http://127.0.0.1:8000
```

Or with Docker:

```powershell
docker build -t naftali-website .
docker run --rm -p 8000:8000 naftali-website
```

## Development Roadmap

Done in the current codebase: Hebrew RTL pages, product and poem APIs, cart foundation, accessibility polish, studio UI styling, and packaging for a single public service.

### Features planned for later

The project is designed to be extensible, so these can be added without rebuilding the core:

* **Authentication & roles** — customer signup / login / logout; secure administrator login; backend-enforced permissions
* **Customer accounts** — saved cart across devices, order history
* **Administrator dashboard** — add / edit / delete products and poems; manage categories; upload product images; view and manage orders
* **Database-backed content** — products, poems, customers, carts, and orders stored in PostgreSQL
* **Payments & checkout** — payment gateway, order confirmation, and completed-purchase flow (currently marked “Coming Soon”)
* **WhatsApp poem newsletter** — subscribe with explicit consent, automatic notice when a new poem is published, and unsubscribe
* **AI studio assistant** — help visitors find products or poems, answer product questions, and prepare orders through OpenRouter on the backend only (API keys never exposed to the frontend)
* **Public hosting** — always-on deploy (for example Render with the existing Dockerfile)
